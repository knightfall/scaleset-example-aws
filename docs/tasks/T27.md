# T27 · Prepare migration and production activation

**Depends on:** [T26](T26.md) and approval from the owners of GitHub routing, each provisioner and controller hosting. **Baseline:** migration strategy is documented. No production runbook/readiness sign-off or activation is established. [Migration strategy](../implementation-plan.md#8-existing-asg-migration-and-rollback)

## Deliverables

Produce an environment-specific rollout and rollback runbook, readiness record and binding inventory. For each profile list purpose, labels/group and exact scope/set ID, backend identity and approved revision, role boundaries, platform, quotas/limits, operator, observability and verified canary references. Record current production settings and GitHub selectors before changes. Identify unresolved live gates, impact, evidence needed, owner and fallback for each. A go/no-go review decides eligibility. Actual production changes require separate approval.

## Migration sequence

1. **Inventory and baseline.** Record runner-group membership and routing, actual busy/assigned work, legacy auto-registration, launch template/version, protection, lifecycle integrations, limits, scale policies, existing writers and current cloud ownership. Confirm role, network, quota, bootstrap protocol, observability and least-privilege checks. Prepare independent scope/label tests. Never count ordinary group runner registrations as scale-set registrations.
2. **Isolated canary.** Prefer dedicated approved capacity and distinct routing. Use an existing compatible ASG, or let its owner prepare approved bootstrap changes. For in-place migration, reserve a handover window and record the legacy owner process to restore. Prove JIT one-job execution, safe scale-in, in-flight preservation, PAT/App rotation as applicable, and required workload paths. Include Linux/Windows, Docker, Fargate-compatible and Copilot cloud-agent canaries only where explicitly part of the environment.
3. **Drain legacy ownership.** Stop routing new work to the legacy selector under the approved sequence. Let old work finish or follow the agreed rerun process. Use authoritative busy/assignment evidence. Disable competing legacy capacity and registration writers through the owner. Quarantine persistent, legacy ephemeral and unknown instances until their owner can retire them. A changed template does not convert an existing legacy instance.
4. **Activate and observe in batches.** After sign-off, apply the approved compatible generation, bind the exact new profile/group/set and verify preflight. Move selected workflows, record job routing, capacity, role isolation, ownership and per-profile alerts. Pause the next batch on identity drift, unknown occupancy, unexplained assignments, missing recovery evidence or failed telemetry. Leave existing work protected.
5. **Rollback and handback.** Restore routing according to the recorded order, stop new admission and drain affected profiles before releasing resource ownership. Keep IAM and watchers until retirement proves cleanup. Authorize only tabulated compatible image/config versions with current schema and rollout rules. Restore owner-managed ASG settings after quiescence and handback proof. Verify stack/template/change-set policy and retained backups. GitHub set deletion and imported-resource changes are separate owner actions.

## Acceptance and sign-off

- Require traceable T23–T26 evidence for each proposed capability, exact role and host, plus actual workflow acceptance for each configured purpose. Do not enable unproven automatic idle retirement, uncertain IAM paths or unsupported ASG weighting.
- Rehearse stop conditions, rollback and on-call escalation in the sandbox. Record owner approvals, allowed limits, intervention thresholds, date/time, expected side effects and validation artifacts. Include both advancing and rollback transitions for each batch.
- Record outstanding assumptions explicitly. A reviewed runbook may be complete with production activation pending. Keep the activation decision, deployment command and resulting evidence separate from implementation and the sandbox record.
