# T16 · Launch and clean up standalone Fargate tasks

**Depends on:** T07, dispatch from [T10](T10.md), and [T15](T15.md). **Baseline:** only SDK wire fixtures and client selection.

## Deliverable

Launch one ephemeral task per authorized allocation. Recover without duplicate tasks and retire only exact tasks verified safe by the lifecycle and provider evidence.

## Requirements

- Persist allocation ID, exact cluster, pinned task definition, immutable requested parameters and digest, one stable token and earliest possible first send. Use `RunTask` with `count=1`, explicit network, approved roles/overrides and nonsecret correlation in `startedBy`/ownership tags. Allow no raw credential or JIT configuration in task overrides. Scope SDK retries and keep the provider replay deadline separate from the lease-bound attempt deadline.
- Treat HTTP success with empty tasks, failure entries, multiple results or identity mismatch as requiring interpretation and readback. Discover possible launches by recorded ARN, `startedBy` or scoped task events. Reissue only the exact token and parameters within the verified replay window. Use the conservative one-hour-from-first-possible-send budget minus safety margin from the plan, revalidated against current AWS contract. After expiry or conflict, use readback and an explicit recovery decision rather than another launch.
- Reconcile versioned ECS state events and periodic polling through eventual consistency. Handle a task that stops before its registration becomes ready. Persist terminal evidence and settle the associated JIT/runner state before reusing capacity.
- Before a stop, verify exact task identity, current cluster/provenance, lifecycle permission and remaining lease. Preserve busy, unknown and ambiguous work. An essential-container exit normally ends the task. Record confirmed cleanup and sanitized evidence, preserving terminal facts outside ECS.

## Durable effect contract

Define the canonical launch request so its replay is byte-equivalent in all provider-relevant fields after any restart, including network ordering, selected roles, attributes and overrides. Persist the request, stable token and earliest possible send before execution. A changed configuration generation cannot silently reconstruct different content for a pending launch. Store task ARN and allocation binding only with exact response/readback evidence. Preserve the original launch window even when a renewed lease supplies a new attempt deadline.

| Observation or boundary | Replay and state rule |
| --- | --- |
| Before durable begin | No send. A provably unstarted intent may be cancelled or rearmed as allowed by T10. |
| Exact task returned | Bind the task with stable allocation identity. Wait for verified readiness and preserve launch facts across duplicate events. |
| Response lost and exact task found | Adopt only the matching cluster/task/request identity under the original intent. Do not send again for the same capacity. |
| Response lost and task not yet visible | Wait/read back or replay identical request within the recorded valid window. Absence from a partial/eventually consistent read is not a definitive rejection. |
| Replay time equals or exceeds deadline, or parameters conflict | Zero additional launch requests. Preserve unresolved capacity or record independently proven terminal outcome. |
| ECS accepts a stop or task emits an intermediate state | Continue to observe the exact task until terminal proof. Preserve running/unknown tasks and settle effects only after relevant evidence. |

Document how tasks share cluster/IP/quota headroom and how the adapter counts in-flight allocations before they are listed by ECS. Expose startup timeout, ambiguous replay and cleanup age as distinct evidence.

## Request format and replay boundary

- Persist one versioned request with exact cluster ARN, task definition ARN, one task, `FARGATE`, canonical subnet and security group lists, public IP disabled, ECS Exec disabled, approved overrides, ownership tags, correlation ID and the token. Tag authorization and role passing remain in T18. Keep allocation and request identity stable across restarts. Use a 35-character `ss-` plus 32 lowercase hex allocation ID as a controller convention for `startedBy`. The current `RunTask` API documents up to 128 supported characters. Use a stable explicit token at most 64 valid ASCII characters scoped to the cluster. See [RunTask](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_RunTask.html) and [ECS idempotency](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ECS_Idempotency.html).
- Give the journal control of retries with per-call `aws.NopRetryer{}`. Anchor a conservative v1 replay cutoff at 50 minutes from the earliest possible first send, leaving ten minutes against the documented shortest token lifetime. Before enabling that value, verify clock skew, request timing and safety margin in T25/T26. An attempt must finish before the current lease and cutoff. At the cutoff or with changed request, no replay. An ambiguous later failure may not settle an earlier unknown launch.
- Bind an exact task ARN only from attributable response or readback. Recover with T15's standalone correlation query, tagged task detail, known task ARN and durable state events. Compare cluster, allocation, revision and identity. Order validated ECS Task State Change events by task ARN and version and confirm against readback where needed. Keep all unresolved launches in the shared headroom while reads lag, including rapid exits and partial responses.
- On stop, identify the exact verified unused or otherwise safe task under T10. A mere startup timeout is insufficient after a handoff could have been consumed. Stop acceptance, desired status and final task state are separate evidence. Observe exact `STOPPED` and retain task death independently from runner completion and registration cleanup. Never use task absence as a reason to start a replacement unless the old effect and capacity are proven safe.

## Acceptance

1. Test count-one requests and every canonical launch field, lost response after task creation, no task or failure response, token mismatch, first-send time and boundary including lease renewal, duplicate and delayed events, immediate stop and List/Describe inconsistency.
2. Assert task count, wire call count and request equality during recovery. Prove no wire launch after replay expiry. Test rejected stop for unknown/currently busy or mismatched tasks and exact-safe cleanup with response loss.
3. Run `go test -race ./tests/sdkcontract ./tests/lifecycle ./tests/reconciler` and `make check` alongside the adapter suite. Confirm AWS service behavior and task preservation in [T25](T25.md).
